## Context & Gotchas

### Architecture / conventions (carried over from prior sessions, still hold — see also prior handoff content, now superseded by this file)
- **Flask + Supabase**: all DB access via `supabase_req()` in `services/supabase.py`. Most of `controllers/public.py` has no try/except — errors intentionally surface as raw Flask 500s. This is *why* schema-mismatch bugs (`is_wip` last session, potentially `shift_*` this session) manifest as bare "Internal Server Error" pages rather than friendly JSON errors, and why "did the migration run?" must always be checked BEFORE trusting new code in production.
- **No sessions/cookies**: app trusts a client-supplied `X-Gateway-Username` header + a `localStorage` session blob (`rgmc_gateway_session` key). Session shape now includes `isDepartmentHead` (already existed before this session, set from `data.is_department_head` in `script.js`/`user.js` login flows) alongside `isAdmin`/`isManagement`/`isDeveloper`.
- **Every authenticated page is a fully self-contained JS file** — there is no shared `common.js`. `loadSession`/`authHeaders`/`escHtml`/`fmtDate`/`fmtDateTime`/`toggleProfileMenu`/`closeProfileMenu`/`showToast`/`_stripHtml` are duplicated verbatim across `admin.js`, `developer.js`, `tasks.js`, `profile.js`, `user.js`, and now `issues_page.js`. When adding a new authenticated page, copy this boilerplate from the closest existing page (`tasks.js` is the cleanest reference) rather than trying to extract a shared module — that would be a much bigger refactor than any single session should take on unprompted.
- **All CSS is one global stylesheet**: `static/style.css` `@import`s ~25 files (`variables.css`, `base.css`, ... `helpdesk.css`, `issue-tracker.css`, etc.), and every authenticated page links only `style.css`. This means CSS classes defined for one page's feature (e.g. `.res-attach-*` from the resolution-attachment flow, `.iss-kpi-*`/`.iss-bars-*`/`.iss-analytics-grid` from admin's Issues tab) are silently available everywhere and should be reused rather than reinvented — confirmed and exploited repeatedly this session (e.g. the Shift day-picker pills reuse `.res-action-item` verbatim in 3 different places; the new Issues page's whole table/filter/KPI/chart visual language reuses admin's classes 1:1). **Exception**: public reporter-facing pages (`fix_view.html`, `issue_view.html`, `epic_view.html`, `dev_item_view.html`) are deliberately self-contained with their own inline `<style>` and do NOT use `style.css` — new public pages should keep following that split, not fight it.
- **`.iss-analytics-grid` is hardcoded to a 3-column layout** (`grid-template-columns: 230px 1fr 200px` in `issue-tracker.css`) — it was designed for exactly (ring chart | wide bar chart | narrow bar chart) and will NOT gracefully hold more than 3 cards. When adding more analytics cards, use a separate inline `display:grid;grid-template-columns:repeat(auto-fit,minmax(240px,1fr))` container (as done this session) rather than trying to stuff more cards into `.iss-analytics-grid`.
- **`shift_age_days`** is now a derived, server-computed field attached to issue rows by `admin_get_issues` and `issues_get_scoped` (both in `controllers/issues.py`) — it means "business-hours days from `created_at` to `resolved_at`" for resolved/closed issues, or "...to now" for open/in-progress ones, using the *assignee's* configured shift (raw wall-clock fallback if unassigned or the assignee has no shift set). Any future feature touching issue "age" or "time to resolve" should read this field rather than recomputing `Date.now() - created_at` client-side, to stay consistent with the shift-aware convention now established across the KPI strip, priority panels, and Analytics tab.
- **`request_to_department_id` (int, FK → `departments.department_id`) is the ONLY real department signal on `issues`** — there is no `site_name`-to-department mapping anywhere. `users.department` is a free-text name string, NOT FK'd to `departments`; resolving one to the other goes through `_dept_id_for(dept_name)` in `controllers/user_page.py` (a simple `/departments?department_name=eq.X` lookup), now imported into `controllers/issues.py` for the new scoped-issues endpoint.
- **Two genuinely different "team issues" concepts now coexist**: `GET /api/user/issues/team` (pre-existing, any logged-in user, broader definition — department-routed OR assigned-to-a-teammate) powers something in the "My Team Workspace" (`user.html`) page; `GET /api/issues/scoped` (new this session, dept-head/admin/management only) powers the new standalone `/issues` page and is deliberately narrower (department-routed only, no teammate-assignment inclusion) since the ask was specifically "filtered by their departments." Don't conflate these when touching either.
